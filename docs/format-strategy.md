# 格式策略：官方 XML 对 AI 友好吗？读写该怎么切？

> 结论：**官方 XML 不适合让 AI 直接读，更不适合让 AI 直接写；但它是很好的"存储/交换"格式。**
> 推荐：**XML 存（不动）／语义 JSON 读（AI 推理用）／ops 补丁写（引擎负责布局与 XML 生成）**。你说的"JSON 只给 AI 读、写走原 XML"方向对，但**写的那一端不该是"手写 XML 文本"，而该是"语义操作 → 代码生成 XML"**。
> 数据来自 373 个真实电路（`_scratch/corpus-xml/`）与从 255 个类抽出的元件表（`spike/netlist-codec/src/registry.json`）。

## 1. 先量化：官方 XML 到底长什么样

| 指标 | 实测 | 含义 |
|---|---|---|
| 元素总数 / 不同 tag 数 | **12,508 / 109** | tag 是 109 个"密码" |
| 属性总数 / 不同属性名 | **36,541 / 167** | 167 个属性名要背 |
| 属性名长度 ≤2 字符的占比 | **95.6%** | `f`、`x`、`r`、`sc`、`v`、`p`、`wf`… |
| 属性值"打包"（含空格的多值）占比 | **30.4%** | `x="32 320 32 80"`、`xy2br="…"` |
| 带 `x` 属性的元素占比 | **87.0%** | `x` 通常是坐标，**但 `<o>` 的 `x` 是标签字符串** |
| 平均每元件属性数 | 2.92 | 看着少，但语义全靠源码 |
| 单字符 tag 的元素 / 类名 tag 的元素 | **11,155 / 1,353** | 两套命名混排 |
| `f`（flags）出现次数 | **11,388** | 位标志，且**值里还有字符串**（`f="x2"`） |

真实样本（`3phasewye.xml`）：

```xml
<x x="-34 349 512 352" f="4" si="24" te="3 Phase Wye-to-Wye Balanced Resistive Load"/>
<o en="1" sp="64" f="x2" p="0">
  <p v="0" sc="320"/>
</o>
<r x="496 80 496 320" f="0" r="150"/>
```

三处"反 AI"的硬伤，随手就能点出来：

1. **tag 与属性名撞名**：`<r r="150">`（tag=电阻，属性=阻值）、`<c c="1e-5">`、`<p p="0">`、`<v v="…">`。同一个字母在不同位置含义完全不同。
2. **同名属性不同义**：`x` 在元件上是 `x1 y1 x2 y2` 四个坐标打包；在根级 `<o>`scope 配置上是 `"input"`/`"output"` 这类标签。
3. **语义不在文件里，在 158 个类的 `dumpXml/undumpXml` 里**：`<S f="0" p="1" li="0" th="2"/>` 的 `p/li/th` 分别是什么、单位是什么、默认值是什么、`f=2` 是哪一位——不读 TS 源码无法知道。我们抽出来的表里，**105 个元件有属性三元组（属性名→字段名→类型），另有 31/85 个 type 的构造参数个数随 flag 变化**。

## 2. 七个维度打分（1–5，越高越友好）

| 维度 | 官方 XML | 语义 JSON（字段名/单位/默认省略） | 紧凑 JSON（短键/数组） |
|---|---|---|---|
| 名称可读性 | **1** | 5 | 2（靠 registry 解码） |
| 结构自描述（打包字段/位标志） | **1** | 5 | 2 |
| 数值语义（单位/默认/范围） | **1**（只在源码） | 4（schema + registry） | 3 |
| 局部可编辑（改一个值） | **4**（文本定位容易，但要知道属性含义） | 4 | 2 |
| 错误可检测 | **1**（导入才报；坐标差 1px = **静默断连**） | 4（schema 即时校验） | 3 |
| token 成本 | **5**（560 KB） | 1（命名 JSON 是 2.29× XML） | **5**（0.32×） |
| 模型先验（见过这种结构） | 3（XML 见过，这种缩写没见过） | **5** | 2 |
| **合计** | **16 / 35** | **28 / 35** | 19 / 35 |

**读法**：XML 赢在体积，输在所有"理解"维度；语义 JSON 赢在理解，输在体积；紧凑 JSON 只在"你先把 registry 当 schema 喂给模型"时才好用。
⇒ 所以不是"XML vs JSON"二选一，而是**按用途分工**。

## 3. 决策：三个通道

| 用途 | 格式 | 说明 |
|---|---|---|
| **持久化 / 与上游互操作 / 用户存档** | **官方 XML**（保持不变） | 零兼容成本；上游 `dumpCircuit()` 继续是唯一落盘格式 |
| **AI 读（理解、推理、讲解）** | **语义 JSON**（`netlist/0.1`） | 字段名而非缩写；单位/默认值/类型来自 registry；坐标默认不输出；nets 命名。**从引擎对象直接生成，不经 XML 文本解析** |
| **AI 读（批量/长上下文/省 token）** | **紧凑 JSON** 或 **网表文本** | 0.32× / 0.19× XML；需把 registry（一次性）当 schema 提供 |
| **AI 写（改参数、增删元件、加探针）** | **ops 补丁 API**（主） | 模型输出意图，引擎负责放置与生成 XML；不产生坐标 |
| **AI 写（整电路替换/复现）** | **语义 JSON + `layout`**（次） | `layout` 由"读"的结果原样回带，1:1 还原 |
| **AI 手写 XML** | **禁止**（除非只改一个已知数值） | 见下节：静默错误面太大 |

## 4. 为什么"写走 XML"是脆弱点

不是"能不能写"，而是"写错了会不会立刻发现"：

- **坐标不重合 = 静默开路**。`makeNodeList()` 按 `getPost()` 坐标合并节点（`SimulationManager.ts:606`）。AI 把一个引脚写成 `496 80`、另一个写成 `496 81`，**不报错，电路是断的**，仿真结果却是"看起来正常的一堆 0V"。
- **`f` 位标志**：同一个元件不同方向的翻转/镜像/开关态都在这里；写错一位，行为变了但 XML 依然"合法"。
- **打包字段**：`x="x1 y1 x2 y2"` 少一个空格、多一个负号，解析器可能仍接受。
- **没有 schema**：官方反序列化只做"读得到就吃"，不做范围/语义校验（`undumpXml` 大量 `parseDoubleAttr(k, default)`）。

**正确姿势**：让 AI 输出"我要在 n1 和 n2 之间加一个 1k 电阻"，由代码：
1. 在两个 net 上各找一个可分裂的导线点（`WireElm.split()`，`WireElm.ts:240`；引擎自己在画线时也会自动分裂，`draggingDone()`，`:263`）；
2. 在新点上放元件、必要时补正交导线、网格对齐（`app.snapGrid`）；
3. 推入 `app.elmList` → `app.needAnalyze()`；
4. 返回 `{ok, id, atoms}` 或 `{ok:false, reason}`。

这条路**不需要整电路自动布局**（那是几天的独立工程），只需要"在已有网络上增量放置一个元件"——工作量小一个数量级，而且正好覆盖 AI 教学场景的 90%（改参数、加探针、加负载、换电源）。

## 5. ops API 草案（写通道）

```json
{ "ops": [
  { "op": "set",    "target": "R1", "prop": "resistance", "value": 2200 },
  { "op": "add",    "type": "ResistorElm", "between": ["n1", "n2"],
    "props": { "resistance": 1000 }, "place": { "mode": "auto" } },
  { "op": "delete", "target": "R1" },
  { "op": "probe",  "target": "R1", "quantity": "current" }
] }
```

返回：

```json
{ "ok": true,
  "applied": 4,
  "created": { "R1": "c17" },
  "atoms": [{ "wireSplit": ["w3", "w11"], "added": ["c17", "w12"] }],
  "unsupported": [],
  "fingerprint": { "t": 0.0004, "stepCount": 12 } }
```

`target` 用"读"时给出的稳定 id（会话内 `WeakMap`，导出时落 `id`）；`between` 用 net id。**全程没有坐标**，坐标由引擎生成。

## 6. 与体积的关系（避免自欺）

- **语义 JSON 不是省 token 的**（2.29× XML）。它省的是"理解成本"和"出错率"。
- 真要省：用紧凑 JSON（0.32×）/网表文本（0.19×），代价是把 registry 当 schema 一次性注入上下文。
- 省 token 的大头来自**去导线（−32.3%）+ 去坐标（−49.3%）**，不是 JSON 语法（去 XML 语法只 −47.6%，但随后加回 JSON 语法又涨回去）。
- **引擎实测**（`node tools/ext.mjs netlist bench`，v0.1.7，语料 372 例）：纯投影聚合 **0.258× XML**、中位 0.257×
  ——比 spike 的 0.331× 更低，因为主路径直接从引擎对象生成（不经过 XML 解析）且剔除空壳段。
- 紧凑格式**有解码器**（`decodeCompact`），正确性判据是幂等律 `encode(decode(encode(nl))) ≡ encode(nl)`
  加内容对拍；解不回来的只有三件，账目写在 `CompactLosses`（坐标 / 导线行 / 未被引用的 net）。
- 紧凑格式**默认自描述**（v0.1.7）：输出带 `t` 类型图例（类型名 + 该类型实际用到的属性名前缀），
  于是"把 registry 当 schema 一次性注入"这条前置依赖消失了。代价实测**每电路 40–560 字节**
  （占自描述体积 37.7%）：聚合 **0.415× XML**（大电路约 19%，小电路 30–60% —— 图例是固定成本，
  电路越小摊得越贵；1/372 例的极小电路上它甚至比 XML 还大）。
  两个口径都要报，因为它们回答的是不同问题：0.258 是"投影本身有多小"，0.415 是"一次不用带 schema 的读有多小"。
  对照：命名 JSON 是 **2.51× XML**，自描述紧凑是它的 **0.165**（省 83%）。
- 图例同时是**编码端的 registry 快照**：解码优先按图例还原字段名（`losses.legendDrift` 记两端不一致），
  所以 registry 重新生成、属性顺序变动之后，历史紧凑数据仍解得对——这是"长期存盘"需要的性质。

## 7. 两条硬约束（写进实现）

1. **单一对象图，两种投影**：真源是引擎的 `elmList` + `nodeList`（运行时对象），不是任何一种文本。
   - `XML = g(engine)`（上游 `dumpCircuit()` 已有）
   - `JSON = f(engine)`（我们的 codec，从对象直接生成，**不经过 XML 文本解析**）
   - 契约测试比的是"两种投影描述的是同一个对象图"（元件集合/参数/引脚划分），不是"JSON 由 XML 解析而来"。这样就不会继承 XML 的歧义（双路 tag、`f` 位标志、`x` 语义重载）。
   - 文本解析（XML/txt → 对象）只用于**离线语料导入**（373 个历史文件），不在主路径上。
2. **写通道只有一个入口**：`ops`。禁止插件/AI 直接改 `elm.nodes[]` 或手拼 XML；所有写入都经过 codec 的 validate + place + serialize，便于审计与回滚（`UndoManager` 已存在）。
