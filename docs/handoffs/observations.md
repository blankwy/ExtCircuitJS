# 计划外观察（跨阶段累积；Lead 逐条裁决，不在当前卡展开）

- [2026-10-26 · manifest 字段 / 声明与执行] `permissions` 在 manifest 里躺了三个阶段，`claims` 只有命令冲突那一处真被读过；`permissions` 从头到尾**没有一行代码读它**。于是"安全模型"实质是注释：`hello` 用着 `ctx.api`、`ext-event` 用着 `ctx.on`，声明里都是空的，谁也不知道。教训：**manifest 的字段分三种——被运行的、被检查的、纯装饰的；区分方法只有 grep 引用点，不是读文档**。加字段时若当轮不接线，就在字段名旁边写"当前无人读取"，否则下一个人会以为它在生效。
- [2026-10-26 · 双端规则 / 单一权威] 权限要同时被运行期（浏览器）与构建期（lint，纯 Node）判定。两份手写的表一定会漂——漂的方式还很隐蔽：lint 说"没问题"、运行期照抛，或者反过来。这次把能力表落成 `packages/plugin-api/permissions.json`：TS 侧 `import` 它、`tools/ext.mjs` 读同一个文件，测试再拿字面量列表双向核对。**"同一条规则要在两个环境执行"时，第一件事是把规则本身抽成数据，而不是把代码抄两遍。**
- [2026-10-26 · 测试维护 / 第二份 manifest] 给 `permissions` 接线后，`plugin-element.browser.test.mjs` 与 `boot.browser.mjs` 立刻红了——它们都用 `activate({ id: "ext-element", entry: "index.js", rev })` 手搓了一份 entry，权限一加就过期。这和上一轮 `reload.browser.mjs` 硬编码"4 个插件"是同一个病：**测试里出现了第二份 manifest**。处置：一律 `fetch("/plugins/plugins.manifest.json")` 取真身再 spread，让测试跟着产品走。
- [2026-10-26 · 权限模型 / 预期管理] 落地时最容易说过头的一句话是"插件被限制了"。实际不是：插件还是同源 ESM，`window` 照样摸得到，绕开 `ctx` 直接拿 app 完全可行。这套东西给的是**能力显式化 + 漏声明当场报错 + 站点能收紧**，隔离要等 B08。写进 README 时把这段放在表格**后面**、用 ⚠ 开头，比藏在文档深处有用——否则下一个看 README 的人会以为它防得住恶意插件。

- [2026-10-26 · 文档钩子 / 语义错位] **`dumpCircuit` / `readCircuit` 是"序列化"，不是"保存/打开"**：撤销快照、崩溃恢复、粘贴、`isModified()` 的文本比较、子电路进出全走它们（`UndoManager.pushUndo`、`writeRecoveryToStorage`、`popContext`…）。如果按名字当成用户动作来挂钩子，插件光是按键就会被叫醒几十次。处置：不给插件"猜"的机会——宿主在包住这两个方法的同时，把 `undoManager.*` / `isModified` / `popContext` / `commands.doPaste` 也包一层来源标记，`meta.source` 里把 `document` 与其它区分开。**教训：「方法名像什么」不能当作「它什么时候被调用」的依据，先数调用点再定语义。**
- [2026-10-26 · 文档钩子 / 过滤方向] 同一个过滤规则在 load 与 save 两侧**方向相反**：save 侧要按 source 过滤（否则污染撤销快照），load 侧绝不能过滤（崩溃恢复读的正是自己写出去的文本）。这条如果只写在文档里，下一个写插件的人一定会抄反——所以示例插件 `plugins/ext-hook` 的两个 hook 一正一反摆在一起，并在类型注释里点明"自己写出去的格式，自己必须无条件认得"。
- [2026-10-26 · 元件事件 / 设计取向] 选中状态只是 `CircuitElm` 上的一个布尔位，改它的地方散落在 MouseManager（框选/拖动）、CommandManager（全选/删除）、UndoManager、菜单里。挨个包方法既漏又绑死私有实现，于是改成**旁观-比对**：听画布与键盘，动作结束后比对"选中集合指纹"（下标序列），变了才发事件。代价是插件自己 `setSelected()` 不会自动发事件——补一个 `refreshSelection()` 手动同步入口，而不是假装支持。
- [2026-10-26 · 契约维护 / 硬编码] `reload.browser.mjs` 里写着"启动应有 4 个插件""卸载后只剩 hello"，`ext-element` 加进 manifest 之后它就已经红了，只是那一轮没人跑它（`*.browser.mjs` 不在 `node --test` 的 glob 里）。**加插件/改 manifest 时必须手工跑一遍脚本清单**（HANDOVER §5 已记）；这类断言应一律从 manifest 派生——写死常量等于给未来埋一个"跟本次改动无关的失败"。
- [2026-10-26 · 浏览器契约 / 坐标] 两个跟产品无关、只跟"什么时候读状态"有关的坑：① 启动电路是异步装载的，`window.ExtCircuitJS` 出现不代表电路落定，基准里会混进 7 个演示元件；② 载入电路后会重绘居中，`transform` 在两帧内还会变，格点→像素的坐标必须等两帧再算，且"点空白"要按画布比例取（否则点到侧栏上，测试看到的是"什么都没发生"）。两条都写进了 HANDOVER 坑位 22。
- [2026-10-26 · 元件事件 / 触发点枚举] "旁观-比对"式设计的成败全在**触发点清单是否覆盖所有变更入口**，而入口是按"用户怎么动"分散的：画布编辑走 canvas 事件、键盘删除走 keyup、**工具栏拖放建元件走 document mouseup**、**菜单动作走 click（而且可能 stopPropagation，只有捕获阶段收得到）**、载入电路则一个事件都没有。前两类靠直觉就能想到，后三类是这次真正漏掉的。教训：写触发点清单时先 `grep` 出全部 mutation 入口（`elmList.push/splice` 共 15 处），再回头找它们的**共同上游事件**；找不到共同上游的（异步载入）必须明确写出"真正的汇合点是 `readCircuit` 返回"并单独接一个观察者，而不是指望"用户总会再点一下"。
- [2026-10-26 · 事件语义 / 时间与来源错配] 把判断合并到 rAF（配 100ms 兜底）对"选择"是对的——按下和松开常常同帧发生，不合并会把一次点击拆成两条。但对"结构变化"是错的：兜底定时器会在 rAF 停摆（无头浏览器常态）时延后触发，等它跑的时候用户已经按了 Delete，于是**删除被标成了 `pointer`**（v0.1.5 的浏览器契约红在这条上，失败信息是"来源应是 keyboard，实际 pointer"）。教训：**合并只适用于高频/连续动作；离散动作要同步判定**，且判定点必须紧跟在"上游处理器之后"（同一元素上后注册的监听器、或目标处理器之后的冒泡阶段）。
- [2026-10-26 · 测试替身 / 假 EventTarget] 自己写的假事件目标如果只按事件名记账（`removeEventListener(t, f)` 无视 capture），那"卸载后监听器清零"这条断言就形同虚设——真实实现里 `addEventListener(t,f,true)` + `removeEventListener(t,f)` 是**静默泄漏**，而假对象会报"已清空"。这次真代码里就有这个 bug，是读代码时发现的，不是测试发现的。修法：假对象按 `type|capture` 分桶，`removeEventListener` 只删对应桶。**测试替身的"宽容度"就是它漏掉 bug 的能力。**
- [2026-10-26 · 基准电路 / 静默失败] 契约测试里手写的电路文本少写一个字段，上游 `readCircuitText` 会抛异常→被自己的 try/catch 吞掉→**元件静默消失**，测试报的却是"count 应该是 2，实际 1"，看上去像事件系统的 bug（浪费了一轮排查）。两条改进：① 基准电路要断言**元件类型列表**而不只是数量，失败信息才指向"导线被吞了"；② 记进 HANDOVER 坑位 28（文本格式每行 5 字段）。

- [2026-10-26 · 插件自定义元件 / ctx.element] **「自定义元件」这条链路的基础设施早就全了，但运行期从没接过线**：`ElementFactory` 有 owner/注销（S3）、`ExtMenus` 有菜单插槽（A06），两者各有契约测试且在绿——可 `installMenuSlot()` 只被测试调用过，`ctx` 里也没有元件相关方法。于是插件想加元件只能自己摸 `window.ExtCircuitJS.app` + 动态 `import("/ElementFactory.ts")`，恰好踩进下一个坑。教训：**「有测试」不等于「产品里在用」——基础设施的测试如果只调用它自己，就证明不了它被接线了**。
- [2026-10-26 · 浏览器契约 / 模块实例] dev 下同一个 cover 模块会有**两份实例**：应用内部导入解析到 `@fs/V:/…/cover/ts/ElementFactory.ts`，而页面里 `import("/ElementFactory.ts")` 是另一个模块 URL，于是两份 classMap；在后者注册的元件，`app.constructElement()` 依然找不到。dev server 跨多次改动不重启时，HMR 的 `?t=` 还会再分叉一条（`plugins-smoke` 因此出现 `commands.length` 两边都是 0 的假失败，重启即绿）。处置：① `window.ExtCircuitJS.elements.factory` 暴露**同一实例**给控制台/测试/MCP；② A06 菜单契约改用该入口 + 独立类名（原实现借用了示例插件的 `ExtShuntElm`，属隐式耦合，断言范围也从"全局条目数=0"收紧到"本次登记项=0"）；③ 浏览器契约前重启 dev server。
- [2026-10-26 · Node 契约 / 加载约束] `ExtElements` 一开始静态 import `CirSim`（取 `dumpTypeMap`）与 `ExtMenus`（注册菜单），`fiber.test.mjs` 立刻红：它以 strip-only 模式加载 `ExtPluginHost`，而 core 的 `CirSim` 图里有不可擦除语法（`CommandPaletteRegistry` 参数属性）。改成"两张表从 `app.constructor` 上取 + 菜单实现由 `ExtBoot` 注入"后才两边都能跑。**这条约束值得当成 cover 层的通用纪律：凡是会被 `ExtPluginHost` 静态引入的模块，都不得拖进 core 的运行时图。**

- [2026-10-26 · MCP / G4 补强] **交接待办 2 写的是「外部 MCP 客户端验证」，实际缺的是服务器本身**。`packages/mcp/src/index.ts` 从 Stage 5 起就是骨架：接口 + 一份与 `tools.ts` 不一致的工具名清单（含并不存在的 `circuit.apply_ops`）+ `createAttachTransport()` 直接抛 "attach transport not implemented yet"；`package.json` 的 bin 还指向这个只有类型声明的文件。之前所有「MCP 全链路」证据（ai-loop / mcp-tools / mcp-bridge）都是**同进程 import `packages/mcp`**，拿得到 bridge 对象、可以绕过协议直连 `bridge.request("step")`——所以协议层（握手/分帧/content 形状）从来没被验证过，任何标准宿主都接不上。本轮补：`stdio.ts`（零依赖 JSON-RPC over NDJSON）+ `backend.ts`（懒启动后端）+ `dev-server.ts`（探活/拉起/回收）+ `cli.mjs`，入口 `node tools/ext.mjs mcp`。**教训：如果一条链路的验收永远在同进程里做，那么「进程边界」这件事就从来没被验过——而外部集成的全部风险恰好都在边界上。**
- [2026-10-26 · MCP / G4 补强] 两处设计取舍值得记住：(1) **懒启动**——握手阶段不碰浏览器。宿主的典型行为是先握手再列工具，真正调用可能隔几分钟；若握手就拉 Chrome，「没装浏览器/端口被占」会让宿主只显示 "server failed to start"（用户无从下手）。改成首次 `tools/call` 才启动后端，这类错误就变成 `isError` 的工具结果（模型能看见、能照着改）。同时顺带把 observations 里记了三遍的债（Stage 1/3/6 都写过「浏览器测试假定 5174 上有遗留进程」）做成一等公民：`ensureDevServer()` 探活 → 复用或拉起 → 退出时按进程组回收，`mcp-stdio.browser.mjs` 用专用端口 5191 强制走「自动拉起」路径并断言退出后端口释放。(2) **补 `sim.step` 工具**——原工具面只有墙钟 `sim.run`，外部客户端拿不到可复现的推进，测量值无法对拍；任务卡清单是 10 工具，这是第 11 个（`mcp-tools` 的精确清单断言同步更新，非弱化）。
- [2026-10-26 · 数值基线] **同一个电路、同样是「跑 2ms」，两种确定性配方给出的值不同：4.7298V vs 4.80356V**。`dist-site.browser.mjs` 用的是手工帧循环（冻结 `Date.now` + 自己调 analyze/stamp/run，帧数由实现决定），`ai-loop` / `mcp-stdio` 用的是桥的 `step {seconds:0.002}`（按 `maxTimeStep` 折算成 400 步）。两者都确定、都可复现，但**不是同一个时刻**。第一次写 mcp-stdio 的基线断言时直接抄了 dist-site 的 4.7298，测试红了才发现这件事。教训：**确定性断言的基线必须连同「配方」一起记录**（步进入口 + 折算方式），只记数字等于埋一个「换个步进方式就红/或更糟：用宽容差掩盖」的坑。此后凡是跨测试引用电压基线，都在注释里写明来源配方。
- [2026-10-26 · 发布后 / Pages 部署] **生产构建其实一直是坏的，只是没人用浏览器打开过 dist**。接"能不能像原版一样上 GitHub Pages"时，把 `dist/` 挂在 `/ExtCircuitJS/` 下用真实 Chrome 打开，最先暴露的**不是**子路径问题，而是启动即崩：`TypeError: Cannot read properties of undefined (reading 'register')`（`registerElements` 里 `CirSim.theApp`），`window.ExtCircuitJS` 永不出现，站点根部署同样复现。根因是 `tools/coverOverlay.mjs` 的 `resolveId` 把 `path.join` 出来的**反斜杠绝对路径**交还给打包器，而 Vite 自己解析同一文件用的是正斜杠 ⇒ Windows 上同一份源码在构建图里成了两个模块 id，`dist` 里出现了两个 `CirSim` 类：`main.ts` 实例化的是 A，`registerElements()` 用的静态字段属于 B。dev 全程走 Vite 自己的解析，所以 10 套浏览器契约一直全绿——这也是它从 Stage 1 潜伏到 v0.1.0 的原因。修复：所有交还给打包器的绝对路径统一转正斜杠（`toId()`）；探针统计构建图 262 个模块、重复 0。**教训：只验证 `ext build` 的退出码不等于验证了产物；任何"产物"类改动都要有一条"把 dist 当站点打开"的验证路径。**
